## 两项裁定与修正

| 项目 | 基线复核 | 修正及实际回归 |
|---|---|---|
| C01 / P1 异常关闭成功 | 原 HostClient 的实际合成子进程以 code=1 或 SIGKILL 退出，close 仍 resolve；code=0 是正常对照。源码链路确认真实 entry 将 DesktopHost.close 错误转为退出码 1，但客户端丢弃了 code/signal | ended 保存真实 code/signal；应用 close 只接受受信任 entry 的无信号、code=0 结果，否则共享同一个 host_cleanup_unconfirmed 失败。reconnect 仍以旧进程退出且通道断开作为重新接管的前提，由新宿主执行既有 guardian/SQLite 对账，不因非零退出永久拒绝恢复 |
| C02 / P2 命令身份丢失 | 原处理函数在 A 确认丢失→B 成功→A 重试时产生第二个 A requestId；创建 Thread 确认丢失重试也分配新 ID。同 Thread 立即重试是正常对照。接收方是明确合成输入，未声称原诊断运行了 React/ProductCore | Run 未确认意图按 Thread 保存完整命令；创建 Thread 单独保存完整意图。确认前保留参数、显示明确重试按钮并暂时禁止编辑；只有收到 Ack 才清除该意图。不同 Thread 不相互覆盖，不按内容去重，不自动重发 |

原 C 报告中“重复关闭共享完成/失败”的实现声明需由本报告修正：原 12 项检查没有覆盖异常 entry 的 close 返回；原立即重试逻辑也不足以证明跨 Thread 幂等。旧通过记录保留其实际范围，不改写为覆盖本次新用例。

## 新增故障证据

- **实际清理缺证据**：在测试自有目录将 guardian 的 cleanup.json 目标变成目录，阻止最后的原子重命名。真实 guardian 已停止 Worker，留下其自己生成的 `.tmp` 收据；Supervisor 因正式收据缺失失败，经实际 entry 传播到 HostClient.close。重复 close 返回同一 Promise 和同一错误对象。重开实际产品库保持 Run unknown、旧审批 denied、全局执行阻断。只在移回原样真实收据后显式 recover，Run 才结算 failed；原请求再查回同一 Ack，文件未写，Run 未增加。没有手工构造 hostClean 或成功收据。
- **关闭中强杀**：对实际正在关闭的 App Server 发 SIGKILL，close 拒绝。等待真实 guardian 收据及 Worker/进程组消失后，由新的 App Server 重开库对账；不以宿主 PID 消失替代后代清理证据。
- **实际主进程提示**：Electron smoke 最后触发同一缺收据故障并调用窗口 close；真正的 main before-quit 收到失败，窗口保持存在并调用“清理尚未确认”警告分支。测试仅截获原生 dialog 方法的调用参数以免人工点击；不声称人工验收了原生弹窗。
- **实际确认丢失**：仅在可信 smoke 模块内，真实 ProductCore 提交并返回后丢弃一次确认。实际 React→preload→main→Node 链路覆盖创建确认丢失、A/B 交错、同 Thread 重试、确认后明确发送相同内容的新 Run，以及相同名称的新 Thread。比对完整命令及 SQLite 快照：原意图重复 ID 不新增实体，新意图获得新 ID；没有给 Renderer 增加故障入口或通用执行 API。
- 原四场景、Thread 隔离/草稿/安全预览及崩溃后显式 reconnect 继续通过。事件读取与重连不会自动重放工具；C01 的 close 失败和异常退出后的恢复准入是两个不同判断。

受信任 desktop-entry 的正常退出约定只用于应用关闭结果；guardian 收据仍是 Worker/后代清理权威。不能把“退出码为 0”推广为任意外部进程或恶意后代的清理证明。
