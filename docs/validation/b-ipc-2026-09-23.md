## 验收事实与范围

`npm run test:product-worker` 共 **30 项通过**。这是混合套件：协议/发送器背压有 2 项单元检查；恶意/重复 wire producer 明确为 SYNTHETIC；其余检查使用实际子进程、SQLite、文件以及所需真实 Pi API。合成输入不是模型事件 fixture。

| 要求 | 实际观察 |
|---|---|
| 真实 OS 边界 | App Server 与 Worker PID 不同，受控 Worker 的普通 fs 和 SQLite 读取合法测试产品库均失败，新建测试库失败且宿主确认不存在新文件；不使用真实数据库 |
| 幂等与权限身份 | 重复产品启动保持一个 Run/有效执行；重复 IPC operation 只持久化一个 Operation、领取一次；身份、计划和 Operation ID 由宿主生成 |
| 审批与真实工具 | 拒绝后目标不存在；允许后 Worker 调用注册的 Pi write；后续新 Worker 经原生引用恢复并调用 Pi edit，宿主核验文件/hash/成果版本 |
| 参数、版本、期限与资源 | 宿主批准摘要/目标/fileVersion/deadline 与 Worker 已归一化输入相符；版本变化、期限到达、expected/loaded resource lock 不符均阻止执行 |
| 消息边界 | 版本/未知字段/hostClean 注入/accessor/超大/旧实例/伪 PID 被拒；当前违规连接被隔离，不解释为完成；复制身份的另一子进程与 Renderer 命令不能路由到当前 Worker |
| 活跃取消 | 取消时已在真实 Pi 工具授权路径中，先见 cancelling，再等待工具失败、Session 释放和真实进程组清理后 cancelled；不是 idle abort 测试 |
| Worker 故障 | SIGKILL 实际发生在 ready 前、待审批、已领取、写完未送结果、Session 创建、替换创建和 rebind 中；关闭/rebind 不发布迟到实例，重复 close 共享完成或失败 |
| App Server 故障 | 持久 dispatch 后立即 SIGKILL（尚未 arm）、ready 前、固定后代运行时均测试；guardian 在宿主死亡后产生清理记录，重开实际产品库后才对账 |
| 未确认副作用 | 已领取但无结果保留 unknown、不重发；写完丢结果时重开库只读核验，mtime 与内容未再变化，成果仍归原 Operation，崩溃 Run 最终 failed |
| 证据丢失 | 同时杀 guardian/Worker 的负向用例没有清理记录，close 共享失败、recover 报 cleanup_evidence_missing、执行名额继续阻断；不凭 PID 或 Worker 自报结算 |
| 固定后代 | 实际父/子 Node 命令的 PID 与进程组消失，心跳文件停止；监听尝试被 OS 拒绝，无意外监听端口记录。没有宣称测过任意恶意后代或开放端口的回收 |
| 原生与订阅恢复 | Pi 自己保存并重开明确合成原生记录；SQLite 保留产品意图和原生引用，不写第二份消息树。跨 Worker/库重开后 snapshot+cursor 衔接无重复回调，旧绑定观察不写入新 Run，事件重放不执行工具 |
| 初始化与迁移 | 真实 v1 测试库升级 v2 后保留排队意图；entry 启动失败产生有审计的 failed Run，后续显式 Run 可派发 |

正常完成每 Run 回收一个 Worker，下一次通过 Pi 原生引用恢复。App Server 是唯一产品库写入者；guardian 不导入 Pi/ProductCore/SQLite，Worker 不导入 ProductCore。宿主依据自己拥有的进程和受保护 nonce 清理记录推导 hostClean；没有接受 Worker 的 hostClean:true 字段。

## 发现的失败与修正

开工三项仓库检查没有原有失败。开发期间的失败与自查更正未隐藏：

- 最终自查发现缺清理记录时虽然名额仍阻断，Run 标签仍为 running；收尾修正通过独立 workerDisconnected 端口标为 unknown 并撤销挂起许可，不伪造 hostClean。实际双进程终止负向检查及完整回归再次通过。

- 嵌套 macOS sandbox_apply 被 OS 拒绝，最初两项进程测试启动失败。改为宿主测试进程使用网络 tripwire，实际 Worker 直接应用独立 OS profile；没有放宽 Worker 文件/网络限制。
- Pi PackageManager 的祖先元数据查询触发狭窄 Node FS read 拒绝。复用 A3 已验证做法：Worker Node read=* 配合 OS 文件数据白名单；SQLite/普通 fs 拒绝均由实际 Worker 再验证，不能称为 Node FS 读隔离。
- 初版宿主误把 artifactPath 返回的相对路径用作 existsSync 绝对检查，允许场景结算失败；修正为 workspace 下核验，原生 write/edit/丢结果恢复均通过。
- 主动 IPC 断开后等待 guardian 的 close 曾使完成 Promise 悬挂；改为观察所拥有 guardian 的 exit，再读取其进程组清理凭据。重跑资源失败、取消、崩溃及缺凭据路径通过。
- 首轮类型检查暴露异构 ToolDefinition 泛型合并和 ChildProcess 闭包窄化错误；分别调用 defineTool 并捕获固定句柄解决，没有 any 或忽略类型错误。

当前限定验收没有未解决阻塞。仍未验证：Windows/Linux 受限模式、通用恶意进程/setsid 后代、掉电和系统重启、打包 ABI、真实账户/模型、CI、新克隆、生产通用沙箱、完整日志/密钥库、UI。文件检查不是原子 CAS。缺清理证据继续 unknown/blocked；不承诺自动解除。监听端口测试是 OS 拒绝，不冒充开放端口回收。
